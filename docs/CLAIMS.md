# What Z Privacy claims, what each claim does not cover, and how to check it

The owner, 19 October 2026: «نجعل ملف مراجعة في git نحدد فيه نقاط الادّعاءات
التي ندّعيها في التطبيق» — a file in git naming the claims the product makes,
so that an outside reader can attack each one through its own proof.

**How to read a section.** Four lines, always the same four:

- **We say** — the sentence the app or the site actually shows, quoted, with
  the key it is stored under (`apps/flutter_app/lib/l10n/app_en.arb`) or the
  page it is on. Not a paraphrase of what we mean.
- **The limit** — what the claim does *not* cover. It is a line of its own, in
  the same type size as the claim, because a limit in a footnote is a limit
  nobody read.
- **The proof** — a test file, a gate number or a source line **that exists in
  this tree at this commit**. A proof that begins with **unproven —** is a
  claim we have not measured; it stays in this file with that word on it,
  because a claim removed from a list is a claim hidden rather than dropped.
- **Measure it yourself** — the command a stranger runs, from the root of this
  repository, with nothing installed that the repository does not name.

`scripts/check_claims.py` (gate **G56**) reads this file on every gate run: it
refuses a section that is missing one of the four lines, refuses a path, gate,
test or sentence key that does not exist, and prints how many claims are proven
and how many are not. So this file cannot quietly rot, and it cannot quietly
grow a claim with no proof.

**What a proof is made of.** Two kinds, and the difference matters more than
the count. A **test** runs this product's own code and measures what it does. A
**gate** — `G1`, `G5`, `G16`, `G43`, `G46`, `G60`, `G61`, `G69` and most of the
others — reads the tree and measures its **shape**: that there is one HTTP
client, that the interface cannot open a socket, that a job's steps are in the
order its own claim needs. A shape gate proves that this code cannot be the
thing it forbids; it is not a recording of the product running, and no number
of them adds up to a network capture, a Windows installation or an audit. That
is why C-04 wears **unproven** with three gates standing behind it: nothing in
this tree runs the application and watches the interface. The outside reviewer
of 23 October 2026 had to work this out from the gates themselves, which is a
thing the file should say rather than leave to be derived.

**What this file is not.** It is not a security audit; nobody independent has
audited this code (C-16). It is the list of things we say, with our own
measurements beside them, offered so that somebody else can try to break them.

## C-01 · Only the protected version is sent to AI through Z Privacy

**We say:** «Only the protected version is sent to AI through Z Privacy.» (key `onlyTheProtectedVersionIsSent`, the first screen; rule 62, after which the «original text» choice was deleted rather than greyed)
**The limit:** the protected text itself travels, and with it the request's own envelope — the provider's address, the time, the model's name and the size of what was sent. Z Privacy hides the values inside the text; it does not hide that you asked, or whom you asked. And a person may copy restored text themselves (C-02): nothing stops a hand.
**The proof:** `z_core/tests/wire_capture.rs` records the request byte for byte on a local server and asserts the body's `content` **is** the safe payload character for character, with no original or vault value anywhere in body, headers or URL; the contract has no door that takes text (gate `G2`, every `send*`/`ask*` signature names `PayloadHandle`); `z_core/src/gateway.rs` carries a `PayloadHandle` and never a string.
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test wire_capture -- --nocapture`

## C-05 · Protection is permanent: a protected word keeps its token for ever

**We say:** «What has already left this session protected can never be unprotected again — not by you, and not by Z Privacy. The key was the only thing that could have done it, and it will not exist. «Undo protection» takes a cover off the text in front of you, never off what has gone.» (key `everyDocumentCanNeverBeUnprotected`, the Sessions room; rules 49–51, 58, 59 and 089)
**The limit:** permanent means *we* cannot undo it — the vault keeps the block and the key for the conversation is gone. It does not mean the model you already sent the protected text to has forgotten it, and it does not mean a copy you made yourself is protected. **And it was not true of one path until 22 October 2026, measured by the owner's own hand in two windows:** a word protected by hand in a **typed request** with no document above it became no block at all — not late, but never, for as long as that bench lived — because the bench never took its session's naming and the writer that keeps a decision asked only about a document's text; thirteen minutes of work, twice, with «Protected as …» on both glasses. Rule 55-ز makes a cover the hand puts on the request an act worth keeping: the session is born of it and the block is written at the press, and the request itself is kept with its covers (session format 7) so closing the window no longer takes it. **And a refusal to write a block was silent:** the count that answered «n words became blocks» used `0` for «the disk refused me» too, so a copy whose vault another window had changed answered «Protected as …, in 5 places» for twenty-four minutes and wrote nothing — paper 102 §2 makes that refusal a state the glass shows, with the cause named. **And the sentence itself said more than the product does, until the outside review of 23 October 2026 graded this claim false:** it said «Every document and every message protected in it can never be unprotected again — not by you», and the reviewer answered with our own tree — the glass carries «Undo protection» (key `undoProtection`) and the guide says «Press a protected word and «Undo protection» takes it back». That door is real and it is right: `undo_last_protection` (`z_core/src/ops/mod.rs`, 096's undo half) takes a cover back **inside the request**, before anything leaves, creating and destroying nothing; the vault block it made stands. So the behaviour was never the fault. What was wrong was a sentence that put no boundary on «never», and the boundary is **what has left**: the text in front of the person is the person's until it goes, and what has gone is past every door. That is measured on a **message**, the thing that leaves by a send; a protected copy somebody saved is a file this product does not hold at all, so no door of ours reaches it either — which is a reading of the doors and not a measurement, and is said here as one. Measured both ways in `a_cover_comes_off_before_it_leaves_and_never_after` — the undo takes the cover off before the send and the value stands in the clear again; after the send all three doors that take a cover back are given a cover each, take it, and what left does not move by one character, through a restart. **The door is not closed by the send, and the sentence does not say it is:** the marks on the text in front of the person survive the send, which is why the sentence names what has gone rather than promising a button stops working.
**The proof:** `z_core/tests/a_block_is_never_deleted.rs` and `z_core/tests/a_block_crosses_a_profile_and_forget_exempts_it.rs` measure that «Forget» writes an exemption and never erases a block, and that a block crosses a client profile; one function writes every exemption, which gate `G40` reads from the source.
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test a_block_is_never_deleted --test a_block_crosses_a_profile_and_forget_exempts_it`

## C-06 · The vault is one encrypted file, and the passphrase is never stored

**We say:** «One passphrase, kept on this device. Everything Z learns while you work — your names, your lists, your decisions — is kept in it.» (key `onePassphrase`), the room with no vault in it yet: «Your names live in one encrypted vault file. It holds your people and their values, encrypted with a passphrase that never leaves this device.…» (key `yourNamesLiveInOneVaultFile`), and the site's own sentence «even the vault file on disk contains no readable name» (`site/en/index.html`)
**The limit:** the encryption is only as strong as the passphrase a person chooses, and an unlocked vault is readable by anything running as that user on that machine. We protect a file at rest, not a machine already taken. **And the vault is not the only file this app writes, which the screen said until the outside review of 23 October 2026 graded this claim false:** «A vault is the only file this app writes» stood in the one list while the core also writes each session's own encrypted file (`sessions/N.zs`, holding the preview copy and the decisions — C-08), the writer's lock beside them, and the settings file, which is **not** encrypted and never holds a person's work (`zcfg_leak.rs` below is what says so). Four file classes, each disclosed in this file and counted from the source by gate `G15`, and a public sentence that said one. **And it was said twice:** a sweep of the one list for the same words — the review looked at the sixteen claims, not at the list — found the Settings room saying «The vault is the one file this app writes» as well, in a sentence whose own job is to explain why a setting will not be there tomorrow. Both are gone; the second one keeps its own promise and loses the file count, which was never its business. **And two more files are written when the person asks for one by name, both by the Dart side and never by the core — which is why `G15`'s census of the core's four classes is still the whole of what the core writes:** a protected copy in the documents folder (`<document name>-<session>-protected-<date>.pdf`, named by the person since 24 October 2026 — a second copy of one day becomes `…-2.pdf` — and the name itself is not protected), and the restored document as a plain PDF at a path the person chooses, which is the only file this product writes that holds values in the clear and carries no footer, no answer page and no claim of protection (`apps/flutter_app/test/the_restored_text_is_saved_as_a_plain_pdf_test.dart`). The sentence now says what the vault **is** rather than that it is alone, and the same stroke went through `README.md` and the release's own `packaging/linux/README.txt`. **And the folder that holds it is narrowed on Unix only:** `z_core/src/secure_file.rs` sets the data directory to 0700, and refuses to write at all when the person has taken a permission off it; the half of that file that is compiled off Unix creates the folder and asks nothing, so on Windows the vault's folder is whatever that machine's own permissions make it. Measured from the other end on 21 October: the Dart contract walk handed the core the machine's shared temp folder, Linux refused it — nobody can narrow a folder they do not own — and Windows accepted it and wrote a vault there.
**The proof:** `z_core/tests/the_vault_file_says_nothing.rs` searches the written file for the names it was taught and finds none; `z_core/tests/zcfg_leak.rs` does the same for the one file that is **not** encrypted; every line in the core that touches the filesystem carries its reason above it and is counted by gate `G15`, which prints the four classes by name — the vault, the session files, the writer's lock, and the settings file in `config.rs` alone (`G15b`); and no function in the whole contract returns a key or a passphrase (gate `G8`).
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test the_vault_file_says_nothing --test zcfg_leak`

## C-07 · Two copies of Z Privacy never lose a write to the vault — the session file's own guard is measured by one copy and a hand

**We say:** «Another copy of Z Privacy changed this vault. Close that window, or lock and unlock here to take in its work.» (key `troubleVaultChangedElsewhere`) — and the guide now says what that sentence does and does not cover: «so a vault write is not lost in silence. What was measured is two copies of Z on one computer sharing one vault; two machines sharing a folder over a network are not, and neither is the file a session keeps, which has a guard and a measurement of its own.» (`site/en/guide/index.html`, narrowed by paper 105 from «nothing is lost silently» — the outside review's finding 2, which read the old words as a promise wider than this claim's own limit)
**The limit:** **the title names the vault because the outside review of 23 October 2026 graded the old headline — «never lose a write» — exaggerated, and what it read to say so is this very line:** a limit a reader has to reach the third sentence of is a limit the headline was contradicting. One machine and one data directory. Two machines sharing a folder over a network file system are **not** measured, and the lock we take (`LockFileEx` on Windows, `flock` on Linux) is not a promise across such a share. **And what it measures is the vault, which is not the whole of what a write is — measured on the owner's own machine on 22 October 2026, two windows over one test folder:** the sentence quoted above **never appeared**, in either window, in either round. The vault's own guard worked and refused the second copy's writes; the refusal was then thrown away by the one function every protect door writes through, so nothing reached the glass. And the session file had no such guard at all: `sessions/1.zs` held a document and eleven decisions at 21:35:03 and held an empty body at 21:35:11 while `vault.zv` did not move. **That was read on 22 October as «a write lost, by an author this tree cannot name» — and on 24 October 2026 the owner named the author, which makes it not a lost write at all.** In that same second he had saved a protected PDF: «أنا حفظت جميع الملفات عن طريق حفظ نسخة PDF», and the Windows session's own entry of 24 October — named here by its commit, `e36c92c`, and not by a path, because that entry is not in every tree — records the 16 751-byte z-pdf written into Documents\ZPrivacy at exactly 21:35:11. The PDF is a **door**; 089 rule 9 takes the preview's copy out at every door that takes text out; and a session holding no turns and no copy **is** an empty body. `the_manual_door_takes_it_out`, in `z_core/tests/the_preview_keeps_what_it_holds.rs`, measures that door doing exactly that. The measurement of 22 October stands as it was taken; what moved is its reading, and it moved in writing rather than quietly. **What the correction does not move is the guard — and this is the place to say what that guard reaches, because nobody had:** every writer of a session's body reads the file first, inside the same lock, so what it catches is a read that went **stale between a read and a write**, and never a press that reads as it writes. The class is real whether or not it caused anything in October; what holds the shape is a census, not a test that could only ever stay green — `crate::conversation::write(` lives in `write_body` alone in the whole of `z_core/src`, which gate `G36` reads. Paper 102 answers that class rather than an author: the session file is now written only over the bytes the body was read from or over nothing at all, a birth looks at the floor before it spends a number, the copy is not written beside a refused block, and both refusals reach the glass in their own words. **The proof:** `z_core/tests/two_copies_never_lose_a_write.rs` runs two processes against one vault — a ready-file handshake, forty trials — and asserts no write is lost silently; the lock is taken for the whole of a core call in `z_core/src/session.rs`, which gate `G43` reads, and the Windows job asks for this test by name (gate `G53`).
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test two_copies_never_lose_a_write -- --nocapture`

## C-09 · Sessions name apart, and the vault reads back: the same name takes a different token in each

**We say:** «Each session has its own encryption. The same name in two sessions takes two different tokens, and in one session it takes the same one wherever it appears — so a session is how you choose what an AI can line up and what it cannot. The keys are all in your vault, so reading a protected file back is the vault’s own door and not a session’s: anything saved from any session in this vault comes back in its real names, and the reading says which session they came from.» (key `eachSessionHasItsOwnEncryption`)
**The limit:** **this claim said «Sessions are isolated» until 24 October 2026, and the owner's own Windows test is why it does not any more.** He built a second session in the test vault, saved a protected PDF from it, ended the process and started it again to rule out memory, unlocked, stood in **Session 1** — and read that file through the z-pdf door. All twenty names came back, naming the session they came from. He expected a wall, and he had that expectation from this very sentence; his verdict on the behaviour was «I think the vault works excellently», so the behaviour stays and the words move. **Naming is per session; the way back is the vault's.** A token minted in one session is unknown in another, and an answer restored inside a chat restores only that session's tokens — that is what a model can and cannot line up, and it is the whole of what a session buys. The z-pdf door (079) is a different act: it reads a protected file into its own names with no bench at all, from **any** session this vault holds, and names the session each name came from. A vault that does not hold that session says so instead and puts nothing back: «This document carries 19 names from a session this vault does not hold (6466). Nothing here can put them back: the key that made them is not in this vault.» So the **vault** is the boundary of who can read back, and the session decides how a value is named. And the *kinds* leak on purpose — a token says `PERSON` or `IBAN`, because a model that cannot tell a person from an account cannot answer. This is about linking across sessions, not about a provider: one provider sees everything you send it.
**The proof:** `z_core/tests/a_token_does_not_cross_a_session.rs` measures that a token minted in one session comes back unknown in another and is never restored; `z_core/tests/the_door_back.rs`'s `the_door_back_reads_a_file_another_session_protected` measures the other half the owner met — a file one session protected, read while a different session is open, comes back in its real names and names the session that made them; `z_core/tests/a_session_carries_its_own_key.rs` measures the key; every token carries a namespace drawn from the operating system every time, with no weaker interim stage — `os_hex4` in `z_core/src/tokens.rs`, which asks `getrandom` and whose fallback mixes the clock rather than panicking. The library's own vectors (C1–C7) live in a different repository (`ZPrivacy-lib`, sealed), so from **this** tree the app side is what is measured.
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test a_token_does_not_cross_a_session --test a_session_carries_its_own_key`

## C-10 · The reader's limits are named numbers, not «too large»

**We say:** the sentences the reader refuses with name the number, e.g. «{size} MiB is past the {limit} MiB limit for one document» (`z_core/src/documents/mod.rs`)
**The limit:** every number is named and every one of them is this reader's. The general limits: a file of 25 MiB, 4 MiB of text after decompression, 8 MiB for one entry inside a zip, 512 entries, 2000 pages, and a swell of at most 200× (measured worst case in the owner's own documents: 95.7×). And the PDF's own two ceilings, which are the ones a bomb meets first: a document may unpack to `max(16 MiB, 32× the file)` (`PDF_UNPACKED_FLOOR`, `PDF_UNPACKED_SWELL` — the pair the owner's 39.50 MiB tax PDF argued for) and no single stream past 8 MiB (`PDF_STREAM_BYTES`). A document inside those numbers is read; one outside them is refused by name rather than read half-way. **And that last sentence is wider than the corpus behind it, which the outside review of 23 October 2026 graded exaggerated:** what is measured is a named set of shapes — a 9 MiB stream, an 8 MiB refusal inside a zip, a 200× bomb, object streams, ToUnicode, forms, cumulative page content, compressed cross-reference tables, and the file/text/page boundaries of the document module's own tests. Not every encoding, not every reader combination, and not every exact boundary of every format. A document inside these numbers is read **as far as this corpus reaches**; a shape nobody has fed it is a shape nobody has measured, and the honest promise is the refusal — a limit this reader meets is named, never silently cut (`a_cut_stream_is_never_a_read_document.rs`).
**The proof:** the numbers are one `limits` module in `z_core/src/documents/mod.rs`; `z_core/tests/a_cut_stream_is_never_a_read_document.rs` measures that a stream cut by a limit is never imported as a whole document; the zip and PDF readers hold their own refusals in `z_core/src/documents/zip.rs` and `z_core/src/documents/pdf.rs`.
**Measure it yourself:** `cargo test -p z_core --features fake_provider,test_clock,measuring --test a_cut_stream_is_never_a_read_document && cargo test -p z_core --features fake_provider,test_clock,measuring --lib documents`

## C-13 · The chat carries only protected exchanges, and the core builds its history itself

## What we do not claim

- **Anonymity from the provider.** Address, time, model, size and the protected text itself travel. A provider knows that you asked and what the shape of it was. Z Privacy removes the values; it does not remove you.
- **Anonymisation.** This is **pseudonymisation**: a token stands for a value and the mapping lives in your vault. A protected text plus knowledge of the world can still narrow down who it is about — a single-patient clinic letter is still about that patient with every name removed.
- **Detection of everything.** The scanner is rules and lists, not a model. The three faults the outside model graded serious on 19 October 2026 (خ3, خ4, خ5) are **closed** — the proof is in C-11 — and what remains open is named here rather than left for a reader to find:
  - **A typographic ligature is still missed.** «ﬁscher» reads as «fischer» only under NFKC, and NFKC is forbidden in this product because it adds a space to the Arabic mark forms and would cut words in two. Measured in `a_ligature_is_still_missed_and_that_is_written_down`.
  - **A date of birth written out in words is still missed.** «12 April 1985» under its own label is not taken: a month-name list is language data and 095 added none. Measured in `a_date_of_birth_written_out_in_words_is_still_missed`.
  - **An amount and the city on a date line are context, not identities** — the review's own ن14, and a written decision rather than a gap.
  - **A card from a network whose prefix is not in the published table is not taken.** The rule asks the checksum **and** the issuer prefix, because one long number in ten passes Luhn by chance — the Arabic letter in this tree holds one that does and is an account number.
- **That review is optional.** Everything the scanner is unsure of is a suggestion, and no door opens while one is unanswered. We do not claim the scanner's first pass is complete — we claim nothing leaves while a word waits.
- **An independent audit.** None by a security firm. One outside model's review exists (19 October 2026); its three serious findings are **closed**, with the proof in C-11, and what it left open is the list above. A review by one reader on one day is not an audit, and we do not present it as one.
- **Every platform.** Linux is measured; Windows is built and measured by the workflow, and its numbers are the ones a run writes into `docs/`. macOS, iOS and Android are not built.
- **That a long chat sends less.** Every later question carries the earlier turns, protected. A chat is cheaper in names, not in bytes.
- **Protection of what you copy yourself.** «Copy Restored» puts real values on the clipboard, after asking. After that it is the operating system's clipboard and other programs may read it.
